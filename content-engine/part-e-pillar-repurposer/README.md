# Part E — Pillar Repurposer

Reference video 1's pipeline, built end to end, with the two paid pieces swapped
for free ones.

```
transcript -> concept -> voice lint -> photo pick -> cover
           -> plates -> render -> self-check -> review -> schedule
```

| Their stack | Here | Cost |
|---|---|---|
| Claude Code as the engine | Python + your existing keys | free |
| **FAL** for the cover image | **a real photo + CSS treatment in headless Chrome** | free |
| HTML for interior slides | same, and it is the default | free |
| **Blotato** for scheduling | **export bundle** (Blotato adapter optional) | free |

Take one long thing the practice already made — a recorded FAQ, a talk, a
YouTube video, a blog post — and cut it into a carousel. Its advantage over
Part C is that the substance is **already theirs**, so there is nothing to
fact-check against an external source and nothing to attribute.

## This lane assumes the source is YOURS

`build --from <url>` **refuses** unless you add `--own-content`. Local files pass
without it.

That guard exists because this lane rewrites the transcript in the client's voice
*and lifts verbatim pull-quotes out of it*. That is exactly right for the
practice's own recorded material and indefensible for anyone else's — it puts
another creator's phrasing and unverified clinical claims into your client's
mouth, and it is the near-duplicate pattern Instagram demotes.

**Someone else's video is not useless — it just belongs in Part D**, which
extracts the abstract structure and never lets the rewrite step see the source.

```
cd ../part-d-reels-engine && python run.py mine && python run.py script --all
```

## Setting up the photo library

This is the part that needs you, and it is worth an hour.

1. Put real photographs of the practice in `assets/photos/`. The treatment room,
   the front desk, the consult room, the building. Empty rooms are fine and are
   usually the safest choice.
2. `python run.py photos scan`
3. Open `assets/photos.json` and write a **description** for each one. That
   sentence is what the picker reads, so describe what the photo *shows and
   feels like*, not the filename.
4. For anything with a patient in frame, set `depicts_patient: true`, a
   `subject_ref`, and `consent: "on_file"` — and add the matching release to the
   consent register. Photos without a release are silently excluded from the
   pool rather than being picked and blocked later.

> The three images shipped in `assets/photos/` are **synthetic test gradients**,
> generated by `fixtures/make_test_photos.py` so the renderer could be verified
> without spending anything. They are not photographs. Delete them.

## How the cover replaces a paid image model

Everything the generated cover in the reference video was buying is CSS:

| Effect | How |
|---|---|
| Golden-hour grade | `filter: saturate() contrast() brightness() sepia()` |
| Vignette | radial-gradient overlay |
| Film grain | inline SVG `feTurbulence`, `mix-blend-mode: overlay` |
| Text legibility | a directional scrim gradient, light or dark |
| Type sitting into the image | text-shadow + scrim, sized to the headline length |

It costs nothing, it is deterministic, and — unlike a generated image — it
cannot produce a sixth finger or a misspelled word, which is the actual failure
mode of AI text-on-image.

**Three variants** are rendered every run because that is what the reference
video does by hand: `editorial-bottom`, `editorial-top`, `band`. They differ in
the things that change stop-rate, not in decoration.

## Self-check, then review

Split deliberately, per the sharpest line in either video:

> *"Almost nothing that went wrong was a taste problem. It was mechanical. That
> should decide where you spend agents versus where you spend code."*

**Self-check (mechanical, free, always runs):** exact canvas size, blank-render
detection, and a real WCAG contrast calculation in the band where the text
actually sits — so an unreadable cover is caught before anyone looks at it.

**Review (taste, one model call):** the model *looks at* the rendered variants
and picks a winner, with a reason and one suggested fix. Falls back to the first
mechanically-clean variant if vision is unavailable.

## Claims: two kinds

Part E introduced a distinction the other lanes now share:

- **`practice_fact`** — about how *this practice* works ("we hold emergency slots
  every weekday morning"). No external source exists; the clinical sign-off gate
  is what attests it.
- **`clinical_general`** — about dentistry as a field ("molars have more canals
  than front teeth"). Needs a citation, and the pillar lane does not have one, so
  the prompt tells the model to cut these rather than assert them.

Getting this wrong is the most common reason a pillar build blocks. `--fix`
handles it automatically most of the time.

## Where it breaks

- **No photos, no covers.** The build still runs and renders plates, but the
  cover step is skipped. Set the library up first.
- **The gate blocks more often here than in Part C**, because a person talking
  freely says things that are fine out loud and not fine as advertising copy.
  That is the gate working. Use `--fix`.
- **Non-determinism.** Two runs of the same pillar produce different carousels.
  Re-run until you like one; the source of truth is `outline.json`.
- **A weak pillar makes a weak carousel.** Under ~120 words and the concept will
  be thin. The build warns you.
